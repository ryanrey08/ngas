# API Page Audit

Every route, tab and data-bearing shell component in `ngas-frontend`, what it shows, what it does, and which API it now uses. This is the implementation checklist for the RTK Query integration (see [API_INTEGRATION.md](API_INTEGRATION.md)).

- Route files: 13 `page.tsx` (8 of them `[tab]` routes) → **50 module tab pages** + 6 standalone pages (`/`, `/login`, `/forgot-password`, `/dashboard`, `/users`, `/settings`) + not-found = **57 routes**.
- Integrated with the centralized API layer: **53 pages** (all 50 tabs + dashboard, users, settings) and 4 shell components (institution switcher, notification bell, footer, journal-entry header buttons).
- No data API needed: `/`, `/login` and `/forgot-password` (auth flow, already wired to the real backend and left unchanged), not-found.

Status legend: ✅ = page inspected, data requirements identified, endpoint implemented, mock data connected, RTK Query hooks used by the page, existing actions connected, loading / error / empty states handled, CRUD / workflow and cache behaviour verified (see *Verification* in API_INTEGRATION.md). ➖ = no API needed.

## Placeholder behaviour that was replaced

| Where | Before | Now |
|---|---|---|
| Every list tab, row “⋮ More” | Toast “Available once connected to the backend” | Workflow menu with the actions valid for the row’s status (approve, reject, post, release, deposit, remit, reconcile, activate…); hidden on read-only registers |
| Auto Journal → Generate Entries | Header button did nothing | Confirms, then `POST /double-entry/auto-journal/generate` creates draft GJ entries |
| Journal Templates → New Template | Header button did nothing | Create form (`POST`), plus Edit from the row menu (`PATCH`) |
| Chart of Accounts → Edit (pencil) | Toast “Editing is disabled in demo mode” | Edit Account modal (`PATCH /coa/accounts/{id}`) |
| Users & Roles → Invite user | Toast “Invitations are disabled in demo mode” | Invite modal (`POST /users`) showing the one-time temporary password |
| Financial Reports → Generate | 600 ms timer + fixed sample | `POST /financial-reports/{code}/generate`; trial balance, AP/AR, collections and cash position are computed from live data |
| Financial Reports → star / fiscal year | Local state / uncontrolled select | `PUT …/favorite` (optimistic); fiscal year and periods from `GET /settings` |
| Posted Entries → drafts | Drafts could be listed but never posted | “Post” row action (`POST /journal-entries/{id}/post`) |
| Institution switcher | Hard-coded list | `GET /institutions`; switching refetches all cached data |

## Remaining gaps

- **No real backend endpoints exist yet** for any accounting module (journals, COA, books, cash, AR, AP, reports, dashboard, notifications, institutions, settings). Those pages run on the mock API; in real mode they show the backend's 404 error. Contracts are in API_INTEGRATION.md.
- The backend's `GET /users` and `GET /roles` only accept `per_page`; the `search` and `filter[role_id]` parameters the Users page sends are an expected extension, so in real mode search/role filter won't narrow the list until the backend supports them.
- Sorting on Users is not offered (the backend orders by creation date only).
- Attachments / Supporting Documents panels on the entry forms are informational only in the existing UI (no upload control exists), so no upload endpoint was added.
- Visual check in the browser was not possible from the automated session (every page sits behind the real backend login). Typecheck, lint, production build and a 48-check API/cache integration script passed; please click through once signed in.
